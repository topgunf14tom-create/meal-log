# 食事管理アプリ改修仕様書（写真解析の再設計と食品DB内蔵化）

作成日: 2026-11-10
目的: 明日以降、この仕様書をもとにClaudeへ実装を依頼するための設計書。

---

## 1. 背景と現行の問題

現行アプリは、食事写真の解析から栄養価の算出までをClaude APIに一任している。この方式には2つの問題がある。

### 1.1 コスト
- 実測: 6食の解析で約 $4（1食あたり約 $0.67）。
- 内訳の大半は画像ではなくテキスト側（毎回送信する長いプロンプト、複数回のコール、再解析）。
- 全食（月約90食）に使うと Sonnet 前提で月約 $60 に達し、商用アプリ（あすけんプレミアム月¥580）の10倍以上になる。

### 1.2 精度
- 写真からは「重さ」と「見えない成分（油・砂糖・タレ）」が原理的に取得できないため、写真のみの全自動推定には誤差 ±40% 程度の天井がある。
- Haiku では自由推定させると的外れな結果が出る。一方 Sonnet で再解析しても精度は大きく改善しない（ボトルネックはモデルの賢さではなく入力情報の不足）。
- 結論: 「モデルに数値まで決めさせる」設計自体を変える。

## 2. 改修の基本方針（役割分担）

| 担い手 | 仕事 |
|---|---|
| モデル（Haiku） | 料理名の候補抽出、基準物との比較による寸法・量感クラスの推定まで。**栄養数値は一切出力させない** |
| 食品DB（アプリ内蔵） | 栄養値の唯一の出どころ |
| アプリ（コード） | DB引きと栄養計算を決定的に行う（同じ入力→同じ結果） |
| ユーザー | 量の最終確認をワンタップで行う（少なめ／普通／多め） |

目標値:
- APIコスト: 1食あたり **$0.10 以下**
- 精度: 写真判定の重量誤差 ±20〜25%、チェーン店は公式値により誤差ほぼゼロ
- DBにない料理だけがAPIの対象。DB検索・計算はオフラインで完結する

## 3. 全体の処理フロー

```
[撮影] 真上1枚＋斜め45°1枚（100円玉を同じ平面に写す）
   ↓
[判定] Haiku へ1コール（構造化JSON出力、§5）
   ↓  料理名候補＋量感クラス＋おおよその寸法
[照合] DB検索（優先順: チェーン公式値 → 成分表 → ユーザー登録食品）
   ↓  候補が複数あればユーザーに選択させる
[量の確定] 推定クラスを初期値として表示。ユーザーがワンタップで補正可能（§6）
   ↓
[計算] 100gあたり値 × グラム数 ÷ 100（チェーン値は1食値をそのまま使用）
   ↓
[記録] 既存の記録・目標対比機能へ（基礎1,700kcal＋活動カロリー、PFC目標 20/25/55 は現行仕様を踏襲）
```

APIコールが発生するのは [判定] のみ。それ以外は端末内で完結させる。

### 3.1 入力経路は4つ（対象によって使い分ける）

| 経路 | 対象 | 値の出どころ | 精度 |
|---|---|---|---|
| A. メニューDB引き | チェーン店・コンビニの定番品（ホットスナック含む） | 各社公式公表値 | 最も高い |
| B. 裏面ラベル読み取り | コンビニ・スーパーの包装商品 | パッケージ裏の栄養成分表示（食品表示法で表示義務あり）を撮影→モデルが数値を転記 | 印刷値そのものなので高い |
| C. 写真判定（§5） | 自炊・個人店・スーパーの惣菜など、表示もDBもないもの | 成分表DB＋量感クラス | 推定（±20〜25%） |
| D. 後入れ手動選択 | 居酒屋など、その場で写真を撮れない場面 | チェーンDB＋定番辞書（`fooddb_izakaya.json`）から選択式で入力。写真・LLM不要（APIコスト0） | 辞書の標準量ベースの推定 |

- 経路Bの実装: モデルには「バーコード付近の栄養成分表示欄から、エネルギー・たんぱく質・脂質・炭水化物・食塩相当量と商品名を転記すること。それ以外は推測しないこと」と指示し、構造化JSONで受け取る。転記ミス対策として、記録前に値をユーザー確認画面に出す。確定した商品はJANコード（写っていれば）と一緒にユーザー登録食品へ保存し、2回目以降は撮影なしで呼び出せるようにする。
- ホットスナックは商品自体に表示がないが、コンビニ大手3社（セブン-イレブン、ファミリーマート、ローソン）は公式サイトで商品ごとの栄養成分を公表しているため、経路AのDBに追加して対応する（ファミチキ、Lチキ、ななチキ、からあげクン等）。
- 経路Dの実装: **フリーワード検索を主導線とする**（カテゴリ別リストから探すプルダウン式は大変なので補助に回す）。食後に検索窓へ「からあげ」「生中」のように打つと、全DB（チェーン＋成分表＋居酒屋辞書＋個人DB）を横断した候補がインクリメンタルに表示され、タップ＋個数で記録する。表記ゆれ吸収（ひらがな⇔カタカナ⇔漢字、§4.4）と別名（生中→生ビール（中ジョッキ）等）に対応し、候補順は利用履歴の頻出順を優先する。付記Aの取り分け比率（人数セットで初期値1/N）と組み合わせて使う。居酒屋チェーン（鳥貴族・魚民など）の品目も同じ検索でヒットさせる。
- スーパーの店内調理惣菜・量り売りは表示義務の対象外で値が存在しないことが多い。経路Cで扱い、「推定」マークを付ける。
- **セイコーマートのホットシェフは公式サイトで栄養成分を公表していない**（2026-11-10確認。店頭の包装ラベルにのみ表示）。北海道出張で頻用するため、購入時にラベルを撮影して経路Bで読み取り、ユーザー登録食品として蓄積する運用とする。チェーンDBに収録したセイコーマート60件はPB包装商品（カップ麺・飲料等）のみ。

## 4. 食品データベース仕様

### 4.1 同梱ファイル（本仕様書と同時に納品）

| ファイル | 内容 | 単位 |
|---|---|---|
| `fooddb_seibunhyou.json` | 日本食品標準成分表（八訂）増補2023年の全食品 2,538件 | 可食部100gあたり |
| `fooddb_chains.json` | 定番チェーン店の公式栄養成分（チェーン別・メニュー別）。**最終版: 73チェーン・10,114件**（2026-11-10、全国チェーンTOP100で公式公表のあるチェーンをほぼ網羅。非公表30チェーン（町田商店含む）、一時取得不可2チェーン=大阪王将=サイトメンテナンス中／すし銚子丸=公式サイト休止中。キッチンオリジンは全カテゴリ収録済み193件。うち惣菜・サラダの52件は公式の表示単位が100gあたりのため `variant` に「100gあたり」と記録） | 公式公表どおり1食（1皿）あたり |
| `fooddb_izakaya.json` | 居酒屋の定番メニュー辞書 52件。成分表の値に標準的な1皿・1杯の量を掛けて換算した推定値（`estimated: true`、換算元の成分表IDとグラム数を `components` に保持）。経路D（後入れ手動選択）用 | 1皿・1杯あたり |
| `fooddb_breakfast.json` | ホテル朝食バイキングの定番辞書 36件。同様式の換算推定値（和食／洋食／サラダ・フルーツ／ドリンク）。経路D用 | 1皿・1杯あたり |

#### DBの配置（端末保存を基本とする）

- 参照DB（成分表＋チェーン）は**アプリ同梱で端末保存**とする。容量は JSON 生で合計約2.4MB、SQLite化（名称インデックス付き）で約1.8MB、gzip圧縮で約270KBと小さく、容量上の問題はない。
- 理由: 全利用者共通の公開データで個人情報を含まない／食事記録はその場で行うためオフラインで検索できることが重要／検索のたびに通信やLLMを使わない（コスト方針と一致）。
- DBにはバージョン番号を持たせ、将来メニュー改定に追従するため「サーバー上の新JSONを起動時に確認して差し替える」更新口だけ用意する（初期実装は同梱のみでよい）。
- 個人DB（自分で登録した食品・JAN登録・記録履歴）は参照DBと分離して端末に保存し、エクスポート機能を持たせる。
- **DB更新ポリシー**: チェーンDBは四半期に1回、公式ソースの更新有無を確認し、変わったチェーンだけ差分更新する（追加・値変更・削除をレポート）。成分表は改訂が数年に1度のため年1回確認で足りる。**過去の食事記録は記録時点の値で固定し、DB更新で再計算しない。**

### 4.2 成分表DBのスキーマ

```json
{
  "source": "日本食品標準成分表（八訂）増補2023年",
  "generated_at": "2026-11-10",
  "items": [
    {"id": 101, "name": "穀類/こめ/［水稲めし］/精白米/うるち米", "group": "穀類",
     "kcal": 156, "protein": 2.5, "fat": 0.3, "carbs": 37.1, "salt": 0.0, "fiber": 0.3}
  ]
}
```

- 欠損値は `null`。推定値（括弧付き表記）は括弧を外した数値として格納し、その旨を `source_note` に記録する。
- アプリ内では出典表記（「日本食品標準成分表（八訂）増補2023年」文部科学省）をどこかに表示すること（データ利用条件）。
- 収載値は増補2023年版（一部食品は2020年版から改訂済み。例: 精白米めしの食物繊維 0.3g→1.5g）。公式データベースとの照合検証では無作為10食品・40項目すべて一致を確認済み。

### 4.3 チェーンDBのスキーマ

```json
{
  "chains": [
    {"chain": "すき家", "source_url": "公式URL", "items": [
      {"name": "牛丼", "variant": "並盛", "kcal": 695, "protein": 21.7, "fat": 23.4, "carbs": 99.8, "salt": 2.4}
    ]}
  ]
}
```

- チェーン店の食事は写真判定をせず、メニュー名で直接このDBを引く（公式値が正解データ）。
- サイズ違いは `variant`（並盛／大盛／特盛など公式バリエーション）で保持し、係数換算ではなく公式値を優先する。
- `variant` が「100gあたり」のレコード（キッチンオリジンの量り売り惣菜・サラダ52件）は、値が100gあたりの表示。記録時は購入グラム数を掛けて計算すること。
- **kcalのみ公表のチェーン**（はま寿司、スシロー、サイゼリヤ、日高屋、山岡家）はPFCが `null`。この場合、勝手な推測値で埋めず、成分表の類似食品で補完するか「PFC不明」として記録する（どちらにするかは実装時にユーザーへ確認）。

### 4.4 照合（マッチング）

- モデル出力の料理名とDB食品名の表記ゆれに対応するため、同義語辞書を持つ（例: 白米⇔ごはん⇔ライス、味噌汁⇔みそ汁）。
- 検索は「完全一致 → 同義語変換 → 部分一致（候補提示）」の順。候補が複数残る場合はユーザーが選ぶ。
- **手入力検索（経路D）のための正規化**: 全DBに検索用インデックスを持たせ、ひらがな入力で漢字・カタカナ表記にヒットさせる（例: 「からあげ」→唐揚げ／から揚げ、「ぽてさら」→ポテトサラダ）。各レコードの `aliases`（別名・略称・読み）も検索対象にする。候補の並びは「完全一致 → 前方一致 → 部分一致」の中で利用履歴の頻出順を優先し、端末内でインクリメンタル検索する（通信・LLM不要）。
- 複合料理（親子丼、カレーライス等）は、将来的に「標準構成（材料と比率）のテンプレート」を持てるよう、データ構造に拡張余地を残す（今回の実装範囲外でよい）。
- ユーザーが確定した料理は「ユーザー登録食品」として端末に蓄積し、次回から照合の優先候補にする。

### 4.5 DBの更新

- DBはJSONファイル差し替えで更新できる構造にする（アプリ更新なしでデータを差し替え可能に）。
- 各DBに `generated_at` と出典URLを保持し、古さが分かるようにする。

## 5. 写真判定仕様

### 5.1 撮影プロトコル（アプリの撮影ガイドとして表示する）

1. **100円玉（直径22.6mm）を料理と同じ平面に置く**（基準物。皿より手前に置かない）。
2. **1枚目: 真上から**（面積とスケールの取得）。
3. **2枚目: 斜め約45°から**（盛りの高さ・厚みの取得）。毎回おおむね同じ角度にする。
4. 自宅では、あらかじめ登録した皿の直径を基準物の代わりに使える（皿登録機能）。

### 5.2 モデル呼び出し

- モデル: **Claude Haiku**。1食につき **1コールのみ**（自動の再解析・Sonnetへの自動エスカレーションはしない。再解析はユーザーが明示的に選んだ場合のみ）。
- **プロンプトキャッシュを有効化**し、固定部（指示文・出力形式・同義語の要点など）をキャッシュ対象にする。
- 画像は長辺1,024px程度に縮小してから送信する。
- プロンプトには手順を明示する:「100円玉=22.6mm。まず皿の直径を推定し、次に各料理の縦横（真上写真）と高さ（斜め写真）を推定し、量感クラスを判定すること。栄養価は推定しないこと。」

### 5.3 出力形式（構造化JSON）

```json
{
  "items": [
    {
      "name": "ごはん",
      "candidates": ["ごはん", "麦ごはん"],
      "size_class": "普通",
      "estimated_grams": 180,
      "footprint_cm": [12, 12],
      "height_cm": 4,
      "confidence": 0.8
    }
  ]
}
```

- `size_class` は §6 の4段階（少なめ／普通／多め／大盛）のいずれか。
- `estimated_grams` は補助情報。最終的なグラム数は §6 の「基準量 × クラス係数」でアプリ側が決め、モデルのグラム推定と大きく違う場合はクラス側を優先する（モデルの数値ブレの影響を受けないため）。
- `confidence` が低い（目安 0.5未満）項目は、記録前にユーザー確認を必須にする。

## 6. 量の仕様（人間感覚の判定を取り入れる）★今回の追加要望

写真からの絶対量の推定は不安定なので、「量」は人間の感覚に近い**段階クラス**を正とし、グラム数はアプリ側の基準表から決める。

### 6.1 量感クラスと係数

各食品カテゴリに「普通 = 基準量（g）」を定義し、クラスごとに係数を掛ける。

| クラス | 係数 | ごはん（基準180g） | 汁物（基準180g） | 主菜・肉魚（基準100g） |
|---|---|---|---|---|
| 少なめ | ×0.7 | 約130g | 約130g | 約70g |
| 普通 | ×1.0 | 180g | 180g | 100g |
| 多め | ×1.3 | 約235g | 約235g | 約130g |
| 大盛 | ×1.6 | 約290g | 約290g | 約160g |

- 基準量テーブルはカテゴリ別にアプリ内に保持し、初期値は上表を目安に実装時に調整してよい。
- チェーン店メニューは係数を使わず公式バリエーション（並盛／大盛）の値を使う（§4.3）。

### 6.2 判定と補正の流れ

1. モデルが写真から `size_class` を推定し、初期値として画面に出す（例:「ごはん: 多め」）。
2. ユーザーはそのままでも確定でき、違うと思えばタップで 少なめ／普通／多め／大盛 を選び直す。**この補正が最終値**。
3. 補正は1項目あたり1タップで完了すること（グラム数の数値入力は任意機能として残してよいが、必須にしない）。

### 6.3 学習（任意・後回し可）

- ユーザーが食品ごとに選んだクラスを端末に記憶し、同じ食品の次回の初期値に反映する。
- 例: そのユーザーの「ごはん」はいつも多めに補正されるなら、次回は初期値を多めにする。

## 7. 計算仕様

- 成分表: `栄養値 = 100gあたり値 × 確定グラム数 ÷ 100`
- チェーンDB: 1食あたりの公式値をそのまま使う（サイズは variant で選択）
- 丸め: kcal は整数、PFC・塩分・食物繊維は小数第1位
- 1食の合計と当日累計・目標対比は現行アプリの仕様をそのまま使う
- 推定ベースの記録（写真判定経由）には「推定」マークを付け、後から見分けられるようにする

## 付記A. 精度・コスト改善策（2026-11-10 追加決定、いずれも実装対象）

### 精度
1. **調理法デフォルト**: 調理法カテゴリごとに油・調味料の定型値（例: 炒め物=油大さじ1、煮物=砂糖小さじ2）を持ち、コード側で自動加算する。モデルに、見えない材料を推測させない。
2. **主食だけ計量ハイブリッド**: 自炊時はご飯・麺など主食だけでもグラム入力できる導線を用意し、入力があれば写真推定より優先する。
3. **履歴による候補並べ替え**: 個人の利用履歴で照合候補を並べ替え、サイズクラスは食品ごとの前回確定値を初期値にする（§6.3の学習を実装対象に格上げ）。

### コスト
4. **ルートBのOCR前段（検証付き）**: 裏面ラベルはまず端末のOCR（iOS Vision等）で転記し、整合性検証（kcal ≒ たんぱく質×4＋脂質×9＋炭水化物×4 との乖離チェック）を通れば確認画面へ、落ちればHaikuの転記にフォールバックする。OCRは加速装置であり本命ではない（ユーザーの家計簿アプリでのOCR低精度の経験を踏まえた設計）。
5. **JANバーコードの端末読み取り**: 端末ライブラリで読み取り、個人DBを照合する。LLMは使わない。
6. **写真の再利用**: 画像ハッシュを取り、同一チェーン・同一メニューの確定済み記録と一致すれば前回結果を再提示してAPIコールを省略する。
7. **トリミング（制約付き）**: 送信前に「皿＋100円玉を含む範囲」で切り出す。**コインを画角外に出してはならない**（基準物が消えるため）。切り出し時に端末で測ったコインのピクセル径をメタデータとして添付する。
8. **出力JSONの最小化**: サイズクラス等は数値コード、キーは短く、説明文は付けない（出力単価対策）。
9. **訂正時の再送禁止**: 品目の訂正は前回の構造化結果＋テキスト差分のみで行い、画像を再送しない。

### 共有・取り分け
10. **取り分け比率（シェア補正）**: 大皿料理を複数人で分ける場合に、自分の取り分比率を掛けて記録できるようにする。全ルート（A/B/C）共通で品目ごとに適用可能にする。操作は最小限に: 飲み会の開始時に人数をセットすると全品目の初期値が 1/N になり、よく食べた・ほとんど食べていない品目だけ比率を変える（プリセット 1/2・1/3・1/4・1/5＋任意％）。比率の乗算はコード側で行う。居酒屋の大皿（枝豆・刺身盛り・鍋など）を想定した機能。

## 付記B. 追加機能（2026-11-10 決定、いずれも実装対象）

11. **「いつもの」ワンタップ再登録**: 頻出の食事（単品・組み合わせ）をホーム画面から検索なしで1タップ再記録できるようにする。
12. **残した分の補正**: 記録後に「半分残した」等を1タップで適用できる係数補正（取り分け比率と同じ仕組みを単独食事にも使う）。乗算はコード側。
13. **1日の区切り時刻の設定**: 深夜の食事を前日分として扱えるよう、1日の開始時刻を設定可能にする（例: 28時区切り=翌4時までを当日扱い）。居酒屋の深夜利用を想定。
14. **予算連動の候補表示**: 検索候補の各品目に、その日の残り予算（kcal・脂質）に対して収まるかを超えるかを表示する（色分け等）。店頭で残量から逆算する使い方をアプリ内で完結させる。
15. **1日の記録のテキスト書き出し**: 1日の記録（品目・kcal・PFC・合計・残り予算）をプレーンテキストでコピー／共有できるようにする。スクリーンショットの代替として、他のAIや人への共有に使う。
16. **バーコード連続スキャン**: 経路B/JANの拡張。複数商品を連続スキャンして1食にまとめて登録できるモードを用意する（コンビニでのまとめ買い想定）。

※不採用: 推定値への不確実性の幅（±表示）は実装しない（ユーザー判断 2026-11-10）。
※不採用（自炊の精度策）: マイレシピ登録、調理前写真、パッケージ重量入力、器ごとの盛り量登録は、手間が増えて使われなくなるため採用しない（ユーザー判断 2026-11-10）。**入力の手間を増やす機能は精度が上がっても採用しない**を設計原則とする。

## 10. 未決事項・注意

- 成分表DBは全食品収録。値の検証結果（公式データベースとの照合）は納品時の報告に従う。アプリ内に出典表記を入れること。
- チェーンDBの収録範囲は納品ファイルのとおり。未収録チェーンは今後JSON差し替えで追加する（§4.5）。
- 写真判定の精度目標（±20〜25%）は「2枚撮影＋基準物＋クラス補正」併用時の目安であり、保証値ではない。推定である旨の表示（§7）を入れる。
- 複合料理のテンプレート展開（§4.4）は今回の範囲外。必要になったら別途仕様を追加する。
